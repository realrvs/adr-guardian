# ADR-Guardian

> **CI-контроль соблюдения Architecture Decision Records.**
> Превращаем ADR из «вики, которую все забывают» в живой контракт, обязательный для merge.

## 🎯 Зачем это нужно

Каждая команда рано или поздно сталкивается с одной и той же проблемой:

```text
    ┌─────────────────────┐         ┌─────────────────────┐
    │  Архитектурное      │         │  Код в продакшене   │
    │  решение принято    │  ╳╳╳╳╳  │  нарушает это       │
    │  в встрече / Slack  │         │  решение            │
    └─────────────────────┘         └─────────────────────┘
              │                                ▲
              ▼                                │
    ┌─────────────────────┐         ┌─────────────────────┐
    │  ADR написан,       │         │  Никто не помнит,   │
    │  похоронен в wiki   │ ──────▶ │  что там было       │
    └─────────────────────┘         └─────────────────────┘
```

**ADR-Guardian** ломает этот цикл, встраивая проверку ADR прямо в CI:

```text
    ┌─────────────────────┐         ┌─────────────────────┐
    │  Разработчик        │         │  ADR-Guardian       │
    │  открывает PR       │ ──────▶ │  проверяет:         │
    └─────────────────────┘         │  • нужен ли ADR?    │
                                    │  • есть ли ADR?     │
                                    │  • валиден ли он?   │
                                    │  • не противоречит  │
                                    │    ли старым?       │
                                    └──────────┬──────────┘
                                               │
                                    ┌──────────▼──────────┐
                                    │  ✅ Merge разрешён  │
                                    │  ❌ Merge заблокирован│
                                    └─────────────────────┘
```

## 🏗️ Архитектура

ADR-Guardian — это **не просто CI-скрипт**. Это часть полноценной **AI-native инфраструктуры**, состоящей из семи слоёв.

```text
╔══════════════════════════════════════════════════════════════════════════════╗
║                                                                              ║
║                          СЕМЬ СЛОЁВ GOVERNANCE                               ║
║                                                                              ║
╠══════════════════════════════════════════════════════════════════════════════╣
║                                                                              ║
║   ┌────────────────────────────────────────────────────────────────────┐    ║
║   │ 1. RULEBOOK         .github/copilot-instructions.md                │    ║
║   │    «Устав проекта»: стек, границы, запреты                         │    ║
║   │    Применяется всегда, автоматически                               │    ║
║   └────────────────────────────────────────────────────────────────────┘    ║
║                                    │                                         ║
║                                    ▼                                         ║
║   ┌────────────────────────────────────────────────────────────────────┐    ║
║   │ 2. OPENSPEC         openspec/changes/<name>/                       │    ║
║   │    «Спецификация изменения»: что строим именно сейчас              │    ║
║   │    Живёт per-change, проходит lifecycle                            │    ║
║   └────────────────────────────────────────────────────────────────────┘    ║
║                                    │                                         ║
║                                    ▼                                         ║
║   ┌────────────────────────────────────────────────────────────────────┐    ║
║   │ 3. SKILLS           .github/skills/<name>/SKILL.md                 │    ║
║   │    «Процедуры»: как это делается у нас + failure modes             │    ║
║   │    Opinionated recipes, переиспользуются                           │    ║
║   └────────────────────────────────────────────────────────────────────┘    ║
║                                    │                                         ║
║                                    ▼                                         ║
║   ┌────────────────────────────────────────────────────────────────────┐    ║
║   │ 4. PROMPTS          .github/prompts/<name>.prompt.md               │    ║
║   │    «Шаблоны вывода»: что должно быть на выходе                     │    ║
║   │    Жёсткая структура, validation gates                             │    ║
║   └────────────────────────────────────────────────────────────────────┘    ║
║                                    │                                         ║
║                                    ▼                                         ║
║   ┌────────────────────────────────────────────────────────────────────┐    ║
║   │ 5. AGENTS           .github/agents/<name>.agent.md                 │    ║
║   │    «Роли»: кто делает + tools + escalation rules                   │    ║
║   │    spec-writer · security-reviewer · adr-writer                    │    ║
║   └────────────────────────────────────────────────────────────────────┘    ║
║                                    │                                         ║
║                                    ▼                                         ║
║   ┌────────────────────────────────────────────────────────────────────┐    ║
║   │ 6. HOOKS            .github/hooks/*.json                           │    ║
║   │    «Принуждение»: детерминированные проверки на событиях           │    ║
║   │    secret-scan · dep-check · pre-deploy-readiness                  │    ║
║   └────────────────────────────────────────────────────────────────────┘    ║
║                                    │                                         ║
║                                    ▼                                         ║
║   ┌────────────────────────────────────────────────────────────────────┐    ║
║   │ 7. MCP              .mcp.json                                      │    ║
║   │    «Связность»: подключение к внешнему миру                        │    ║
║   │    postgres · github · adr-index · internal-api                    │    ║
║   │    Read-only first · pinned versions · logged activity             │    ║
║   └────────────────────────────────────────────────────────────────────┘    ║
║                                    │                                         ║
║                                    ▼                                         ║
║   ┌────────────────────────────────────────────────────────────────────┐    ║
║   │              ADR-GUARDIAN (CI)                                     │    ║
║   │              Финальная валидация перед merge                       │    ║
║   │              Тяжёлая проверка, недоступная для hooks               │    ║
║   └────────────────────────────────────────────────────────────────────┘    ║
║                                                                              ║
╚══════════════════════════════════════════════════════════════════════════════╝
```

**Ключевой инсайт:** слои 1–5 **вероятностны** (модель *может* следовать инструкции). Слои 6–7 **детерминированы** (проверка *гарантированно* сработает). Это не дублирование — это **defense in depth**.

## 🔄 Как это работает

### Полный цикл изменения

```text
    ┌──────────────┐
    │   ТИКЕТ      │  "Добавить OAuth-логин"
    └──────┬───────┘
           │
           ▼
    ┌──────────────────────────────────────────────────────────┐
    │  spec-writer agent                                       │
    │  • читает rulebook                                       │
    │  • использует skill "openspec-proposal"                  │
    │  • следует prompt "spec-from-ticket"                     │
    │  • создаёт openspec/changes/add-oauth/spec.md            │
    └──────┬───────────────────────────────────────────────────┘
           │
           ▼
    ┌──────────────────────────────────────────────────────────┐
    │  adr-writer agent                                        │
    │  • читает adr://index (MCP)                              │
    │  • использует skill "adr-writing"                        │
    │  • следует prompt "adr-from-diff"                        │
    │  • создаёт docs/adr/0013-oauth-provider.md               │
    └──────┬───────────────────────────────────────────────────┘
           │
           ▼
    ┌──────────────────────────────────────────────────────────┐
    │  Разработчик пишет код                                   │
    │  • hook postToolUse: validate-adr-format.sh              │
    │  • hook preToolUse: check-adr-required.sh                │
    └──────┬───────────────────────────────────────────────────┘
           │
           ▼
    ┌──────────────────────────────────────────────────────────┐
    │  PR открыт                                               │
    │  • security-reviewer agent читает diff (MCP github)      │
    │  • проверяет против OWASP + ADR                          │
    │  • выносит verdict                                       │
    └──────┬───────────────────────────────────────────────────┘
           │
           ▼
    ┌──────────────────────────────────────────────────────────┐
    │  ADR-GUARDIAN (CI)                                       │
    │  ✅ ADR существует                                       │
    │  ✅ ADR валиден по MADR                                  │
    │  ✅ Нет конфликтов с ADR-0007                            │
    │  ✅ Sensitive files покрыты                              │
    └──────┬───────────────────────────────────────────────────┘
           │
           ▼
    ┌──────────────┐
    │   MERGE      │
    └──────────────┘
```

### Разделение Hooks и CI

```text
┌────────────────────────────┬────────────────────────────────┐
│  HOOKS                     │  CI (ADR-Guardian)             │
├────────────────────────────┼────────────────────────────────┤
│  Inline с агентом          │  На merge / PR                 │
│  Секунды                   │  Минуты                        │
│  Мгновенная обратная связь │  Финальная валидация           │
│  Блокирует действие агента │  Блокирует merge               │
├────────────────────────────┼────────────────────────────────┤
│  • secret-scan             │  • полный ADR-аудит            │
│  • dep-check               │  • тесты                       │
│  • adr-format-check        │  • security review             │
└────────────────────────────┴────────────────────────────────┘

  ПРАВИЛО: < 5 сек → hook.  > 5 сек → CI.
```

## 🚀 Установка

### Быстрый старт

```bash
# 1. Клонировать репозиторий
git clone https://github.com/realrvs/adr-guardian.git
cd adr-guardian

# 2. Установить зависимости
pip install -r requirements.txt

# 3. Создать первый ADR
cp docs/adr/template.md docs/adr/0001-record-architecture-decisions.md

# 4. Проверить локально
export CHANGED_FILES="docs/adr/0001-record-architecture-decisions.md"
python adr_checker/main.py
```

### Подключение к существующему репозиторию

```bash
# 1. Скопировать CI workflow
mkdir -p .github/workflows
cp adr-guardian/.github/workflows/adr-check.yml .github/workflows/

# 2. Скопировать скрипты
cp -r adr-guardian/scripts/ ./scripts/
cp -r adr-guardian/adr_checker/ ./adr_checker/

# 3. Создать структуру ADR
mkdir -p docs/adr
cp adr-guardian/docs/adr/template.md docs/adr/
```

## 📈 Фазы внедрения

```text
╔══════════════════════════════════════════════════════════════════════════════╗
║                                                                              ║
║  ФАЗА 1                    ФАЗА 2                    ФАЗА 3                  ║
║  Human-first               Agent-led,                Autonomous,             ║
║                            human-supervised          human-governed         ║
║                                                                              ║
║  ┌──────────────┐          ┌──────────────┐          ┌──────────────┐       ║
║  │              │          │              │          │              │       ║
║  │  🤖 + 📊     │          │  🤖→🤖→🤖→👤  │          │  🤖🤖🤖→👤    │       ║
║  │              │          │              │          │              │       ║
║  └──────────────┘          └──────────────┘          └──────────────┘       ║
║                                                                              ║
║  CI предупреждает          CI блокирует             CI генерирует           ║
║  (warning)                 merge (error)            черновик ADR            ║
║                                                                              ║
║  • Validate format         • Block on missing       • LLM drafts ADR         ║
║  • Suggest ADR             • Auto-generate          • Semantic check         ║
║  • Non-blocking            • Human approves         • Human only governs     ║
║                                                                              ║
║  Impact:                   Impact:                  Impact:                  ║
║  ↑ Awareness               ↑ Compliance             ↑ Autonomy               ║
║                                                                              ║
╚══════════════════════════════════════════════════════════════════════════════╝
```

### Фаза 1: Human-first (неделя 1–2)

- CI **предупреждает**, но не блокирует merge.
- Разработчик видит: «Вы изменили `Dockerfile`, но не обновили ADR».
- **Цель:** повысить осведомлённость.

### Фаза 2: Agent-led, human-supervised (неделя 3–6)

- CI **блокирует** merge при отсутствии ADR.
- Скрипт **автоматически генерирует** шаблон нового ADR.
- `adr-writer` agent помогает сформулировать Context и Consequences.
- **Цель:** невозможно протащить архитектурное изменение «втихую».

### Фаза 3: Autonomous, human-governed (неделя 7+)

- Интеграция с LLM для **черновика ADR**.
- **Семантическая проверка** конфликтов с существующими ADR.
- Человек только ставит статус «Принято».
- **Цель:** архитектурный надзор становится автономным.

## 💡 Примеры

### Пример 1: Валидация формата ADR

```markdown
# docs/adr/0013-oauth-provider.md

* Статус: предложено
* Дата: 2026-09-28

## Контекст и постановка проблемы
...

## Принятое решение
...

## Последствия
...
```

CI проверяет:

```text
✅ Заголовок присутствует
✅ Статус присутствует
✅ Дата присутствует
✅ Секция "Контекст" присутствует
✅ Секция "Принятое решение" присутствует
✅ Секция "Последствия" присутствует

→ ADR валиден
```

### Пример 2: Блокировка merge

```text
PR #142: "Update Dockerfile for multi-stage build"

Изменённые файлы:
  ✏️  Dockerfile
  ✏️  .github/workflows/deploy.yml
  ✏️  src/config.py

ADR-Guardian проверяет:
  ❌ Изменены sensitive files: Dockerfile, deploy.yml
  ❌ Не найден новый/изменённый ADR в docs/adr/

→ MERGE ЗАБЛОКИРОВАН

Решение: запустить prompt "adr-from-diff" или создать ADR вручную.
```

## ❓ FAQ

**Q: Почему не просто попросить разработчиков писать ADR?**

A: Потому что это не работает. ADR без принуждения — это документация, которую никто не читает. CI делает соблюдение **механическим**, а не **добровольным**.

**Q: Не будет ли это замедлять разработку?**

A: Фаза 1 — нет (только warning). Фаза 2 — добавит 5–10 минут на PR. Фаза 3 — наоборот, ускорит, потому что агенты делают черновики ADR автоматически.

**Q: Что если ADR не нужен для моего изменения?**

A: Используйте `# adr-skip` в описании PR. Но CI всё равно проверит, что изменение не затрагивает sensitive files.

**Q: Чем это отличается от OpenSpec?**

A: OpenSpec отвечает на вопрос «что строим» (спецификация фичи). ADR-Guardian отвечает на вопрос «почему так устроено» (архитектурное решение). Они **дополняют** друг друга.

**Q: Обязательно ли использовать все семь слоёв?**

A: Нет. Начните с Rulebook + ADR-Guardian (CI). Добавляйте Skills, Agents, Hooks, MCP по мере роста. Полная архитектура — это **направление**, а не требование на день 1.
